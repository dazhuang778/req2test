## Context

当前测试人员需要手动阅读需求文档、分析业务流程、手写测试用例，效率低且覆盖率依赖个人经验。本工具是一个独立的本地 Python CLI 项目，不与现有代码库耦合。

技术约束：
- 运行环境：本地命令行，Python 3.10+
- LLM 接口：仅支持 OpenAI 兼容 REST API（通过 base_url 切换供应商）
- 输入格式：固定三段式 MD 模板（文档概述 / 规划功能 / 验收标准）
- 流程图格式：Mermaid，嵌入 MD 文件的 \`\`\`mermaid 代码块中

## Goals / Non-Goals

**Goals:**
- 解析三段式 MD 需求文档，提取流程图和功能设计内容
- 两段式 LLM 调用：先生成测试点 → 用户确认 → 再生成完整测试用例
- 测试用例五字段（编号/标题/前置条件/步骤/预期结果）按模块分组编号
- Pydantic 校验 LLM JSON 输出，失败自动重试最多 3 次
- 导出标准 Excel，每行一个测试用例
- config.yaml 配置 LLM 连接参数，自动从当前目录查找

**Non-Goals:**
- 图形界面（GUI / Web UI）
- 本地离线模型支持（Ollama 等）
- 非 MD 格式输入（Word、PDF 等）
- 递归扫描子目录（目录模式只扫描一层）
- 跨文档合并输出到单一 Excel
- 测试用例管理、版本控制、与 TestRail 等平台集成
- CI/CD 自动化触发

## Decisions

### 决策 1：使用 openai SDK + base_url 实现多供应商兼容

**选择**：使用 `openai` Python SDK，通过 `base_url` 参数切换供应商（OpenAI / Claude / 通义千问 / 其他兼容接口）。

**理由**：几乎所有主流 LLM 供应商均提供 OpenAI 兼容接口。用同一 SDK 统一调用，用户只需修改 config.yaml 即可切换，无需安装多个 SDK。

**备选**：`httpx` 直接调 REST API —— 增加维护成本，放弃。

---

### 决策 2：两段式 LLM 调用（测试点 → 用例）

**选择**：Pass 1 生成测试点列表（含模块前缀），展示给用户确认；Pass 2 批量为每个测试点生成五字段测试用例。

**理由**：
- 一次性生成容易遗漏场景，两段式让 LLM 先"思考覆盖面"再"填写细节"
- 中间暂停给用户修正机会，避免错误方向浪费 API 调用
- 每个测试点独立请求，失败可单独重试，不影响整体

**备选**：一次性生成全部用例 —— 结构不稳定，覆盖面不可控，放弃。

---

### 决策 3：Pydantic v2 校验 LLM 输出 + 最多 3 次重试

**选择**：定义 Pydantic 模型作为 LLM JSON 输出的 schema，使用 `model_validate_json()` 校验；失败则附带错误信息重新请求，最多 3 次。

**理由**：LLM 偶发格式错误（多余文字、字段缺失、嵌套不对）。Pydantic 提供清晰的错误信息，可直接附回 prompt 引导 LLM 修正。

**备选**：手动 JSON 解析 + try/except —— 错误信息模糊，重试效果差，放弃。

---

### 决策 4：正则 + 状态机解析 MD，不引入重量级 MD 库

**选择**：使用正则表达式按固定标题（`## 文档概述` / `## 规划功能` / `## 验收标准`）分割文档，在"规划功能"段内进一步提取 \`\`\`mermaid 块和其余文本。

**理由**：模板固定，不需要通用 MD AST 解析器。正则方案零依赖、易调试、性能好。

**备选**：`python-markdown` / `mistletoe` —— 对于固定模板过度设计，放弃。

---

### 决策 5：模块前缀由 LLM 推导，不维护映射表

**选择**：在 Pass 1 prompt 中要求 LLM 同时输出 `module_prefix`（英文大写缩写，如 `LOGIN`），作为用例编号前缀。

**理由**：模块名是中文，用 LLM 推导英文缩写比手动维护映射表更灵活。缩写在 Pass 1 确认时即展示给用户，可在下一步修正（通过 prompt 参数覆盖）。

**风险**：同一模块在不同文档中可能推导出不同缩写 —— 可接受，当前版本无跨文档一致性需求。

### 决策 6：目录模式下每个 MD 文件独立处理，顺序执行

**选择**：`-i` 参数接受文件路径或目录路径。当传入目录时，扫描该目录下所有 `.md` 文件（不递归），顺序处理每个文件，各自输出 `{原文件名}_cases.xlsx` 到 `-o` 指定的目录。

**理由**：
- 每个 MD 文件对应独立模块，输出也应独立，便于定位和使用
- 顺序执行保留了确认交互（每个文件单独确认测试点），避免全自动跳过审查
- `-o` 在单文件模式下是文件路径，在目录模式下是输出目录，行为一致直觉

**备选**：
- 并行处理 —— 破坏交互式确认流程，放弃
- 合并到一个 Excel（多 Sheet）—— 用户明确要求独立输出，放弃

---

### 决策 7：测试点确认阶段支持多轮对话调整

**选择**：在展示测试点后，将确认提示改为三态输入：
- 输入 `y` / 回车 → 确认，进入 Pass 2
- 输入 `n` → 取消退出
- 输入其他任何文字 → 视为对话消息，追加到 LLM 对话历史，重新生成测试点并展示，循环等待

对话历史以 `messages` 数组维护，包含 system prompt、原始文档内容、所有历史对话轮次，确保 LLM 有完整上下文。

**理由**：多轮对话让用户可以自然语言精调测试点（"增加验证码场景"、"去掉管理员相关用例"），比重新运行命令更流畅。维护 messages 历史是 OpenAI SDK 的标准模式，零额外依赖。

**备选**：只支持 `--context` 一次性注入 —— 不够灵活，无法针对生成结果做迭代调整，放弃。

---

### 决策 8：`--context` 参数作为全局额外上下文注入所有 prompt

**选择**：`--context` 字符串注入 Pass 1（测试点生成）的 system prompt，作为测试重点说明。目录模式下对所有文件生效。

**理由**：用户在运行前已知需要特别关注的方向（如"侧重安全测试"），提前注入比每次对话输入更高效。与多轮对话互补：`--context` 设定全局方向，对话负责局部微调。

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| LLM 输出 JSON 格式不稳定 | Pydantic 校验 + 3 次重试，每次附带上次错误 |
| 大型文档超出 token 限制 | 按 MD 二级标题（`##`）分块，每块独立调用 |
| 模块前缀推导不一致 | 用户在确认测试点时可见前缀，CLI 支持 `--prefix` 覆盖参数 |
| config.yaml 中 API Key 明文存储 | 同时支持环境变量 `TESTGEN_API_KEY` 覆盖，文档提示加入 `.gitignore` |
| 测试点数量多时 Pass 2 耗时长 | 显示进度条（`click.progressbar`），支持 Ctrl+C 中断并保存已生成部分 |
| 多轮对话无限循环 | 每轮对话展示后明确提示操作说明，无最大轮次限制（用户主动控制） |
| 目录模式下部分文件处理失败 | 单文件失败记录错误并继续处理其余文件，结束时汇总成功/失败列表 |
